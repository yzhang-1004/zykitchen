# 菜谱库导入功能方案

> 版本：v1.3 | 日期：2025-06-08 | 状态：已实现（本地搜索 + 无分类筛选）

---

## 1. 需求描述

新增菜品时，如果菜谱库里有这道菜，可以直接导入菜谱（食材+步骤），不需要手动输入。

数据来源：[howtocook 项目](https://github.com/jasonbai/howtocook) — 356 道家常菜菜谱。

---

## 2. howtocook 项目调研

### 2.1 数据结构

每道菜谱是一个 Markdown 文件，包含：
- **菜名**（文件名）
- **难度**（★ 评级，1-5星）
- **食材清单**（必备原料和工具）
- **用量**（计算 - 每份用量）
- **做法步骤**（操作）
- **小贴士**（附加内容）

### 2.2 分类目录

| 目录名 | 对应分类 | 数量 |
|--------|----------|------|
| meat_dish | 肉菜 | 103 |
| vegetable_dish | 素菜 | 60 |
| staple | 面食/主食 | 58 |
| drink | 饮品 | 23 |
| soup | 汤品 | 22 |
| aquatic | 水产 | 27 |
| breakfast | 早餐 | 25 |
| dessert | 甜品 | 19 |
| semi-finished | 半成品 | 10 |
| condiment | 酱料 | 9 |

### 2.3 分类映射

我们项目有 4 个分类，映射关系：

| 我们的分类 | howtocook 目录 |
|-----------|---------------|
| 肉菜 (meat) | meat_dish, aquatic |
| 素菜 (vegetable) | vegetable_dish, soup |
| 面食 (noodle) | staple, breakfast |
| 饮品 (drink) | drink, dessert |

## 3. 方案设计

### 3.1 数据处理

1. **本地解析**：克隆 howtocook 仓库，用脚本解析 356 个 Markdown 文件
2. **转 JSON**：每道菜提取为结构化数据：
   ```javascript
   {
     name: "红烧肉",
     category: "meat",        // 映射后的分类
     categoryName: "肉菜",
     ingredients: ["五花肉", "生姜", "大葱", "料酒", "酱油", "冰糖", "八角"],
     recipe: "1. 五花肉切块...\n2. 冷水下锅焯水...\n3. ..."
   }
   ```
3. **打包进代码包**：生成 `data/recipes.js`（335KB JS module），随小程序发布

### 3.2 数据架构（本地方案）

菜谱数据直接打包在小程序代码包里，**不需要云数据库集合**。搜索在本地完成，无网络延迟。

- 数据文件：`data/recipes.js`（352 道菜谱，335KB）
- 加载时机：懒加载，用户首次点击"从菜谱库导入"时才 require
- 搜索方式：本地 JS Array filter（关键词 + 分类筛选）

### 3.4 搜索逻辑

- 本地 JS Array.filter 匹配菜名（toLowerCase includes）
- 无分类筛选（菜谱库保留原始分类，用户只需按菜名搜索）
- 每次返回最多 20 条
- 输入防抖 500ms

## 5. 数据流程

### 数据准备（已完成）
1. 克隆 howtocook 仓库到本地
2. 运行 `scripts/parse_recipes.py` 解析 Markdown → 生成 `scripts/recipes.json`（352 道）
3. 运行 `scripts/make_js.py` 转为 `data/recipes.js`（335KB JS module）
4. 打包到小程序代码包内

### 用户使用时
1. 新增菜品时点击"📖 从菜谱库导入"
2. 首次打开弹窗时懒加载本地数据（335KB，一次加载后续缓存）
3. 输入关键词或切换分类 → 本地过滤 → 显示结果
4. 点击某道菜 → 自动填充表单

## 6. 兼容性

- 菜谱库是可选功能，不影响现有新增/编辑流程
- 用户仍可手动输入所有信息
- 旧菜品不受影响
